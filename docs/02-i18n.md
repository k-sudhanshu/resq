# RESQ — Language Design: English & Hindi (v2)

This is the document v1 was missing. It defines where each kind of
text lives, how the two languages stay separated, and how language
flows through every layer — URL to prompt to safety filter.

## 1. The one rule

> **Machine-facing text is always English. Human-facing text exists
> exactly once per language, in that language's own tree.**

Machine-facing (English only, always): code, identifiers, config keys,
question/option/category/source IDs, enum values (`CRITICAL`,
`other_adult`, …), API error codes, log lines, git history.

Human-facing (per-language trees, never mixed inline): UI strings,
category labels, questions and options, fallback guidance, disclaimer
and privacy copy, error messages shown to users, AI-generated guidance.

Consequence: the API and database never contain Hindi *keys* and never
contain English *display strings* destined for a Hindi user. A Hindi
user's entire experience is Hindi; the developer's entire debugging
experience is English.

## 2. Where each kind of text lives

| Text | Home | Format |
|---|---|---|
| Frontend UI strings | `frontend/messages/en.json`, `frontend/messages/hi.json` | next-intl message files, identical key sets |
| Categories, questions, fallback guidance, source labels | `backend/app/content/en/**`, `backend/app/content/hi/**` | YAML, identical file names and key structure |
| Safety filter banned phrases | `backend/app/content/safety/en.yaml`, `safety/hi.yaml` | per-language lists (not translations of each other — each list targets unsafe phrasing natural to that language) |
| AI system prompt | `backend/app/prompts/system.txt` | **English** (single file — see §5) |
| AI output | generated per request | requested language |

**Parity is enforced, not hoped for.** A startup check and a CI test
assert that `content/en` and `content/hi` contain the same files, the
same IDs, and the same structure — and that the two `messages/*.json`
files have identical key sets. A missing Hindi translation fails the
build; it cannot ship as silent English leakage.

### The one deliberate exception to full separation

The landing-page category cards show a small second-language label
(design decision from the mockups: "Burn / जलन") so a Hindi speaker on
an English screen still recognizes the right card. To support this,
`GET /v1/content/categories` returns `label` (requested language) plus
`label_alt` (the other language). Everything past the landing page is
single-language.

## 3. Language flow, end to end

```
URL locale prefix  ──►  UI strings  ──►  lang param on API calls
   /hi/assess/burn      messages/hi.json     ?lang=hi  /  "language": "hi"
                                                  │
                                     content registry serves hi/ tree
                                                  │
                                     prompt: system (EN) + output-language
                                     instruction + user data block (as typed)
                                                  │
                                     Gemini answers in Hindi
                                                  │
                                     schema check → hi banned-phrase filter
                                     → Devanagari output check
                                                  │
                                     stored with language="hi", rendered as-is
```

- **Locale in the URL** (`/en/...`, `/hi/...`) via next-intl
  middleware. Shareable, bookmarkable, no hidden state. The toggle in
  the top bar swaps the prefix and keeps the rest of the path.
- **Persistence:** chosen locale saved in the `NEXT_LOCALE` cookie;
  first visit with no cookie lands on `/en` (English default, one-tap
  switch always visible per the design).
- **Every API call that returns or produces human text carries an
  explicit `lang`.** The backend holds no language state; the session
  row records `language` for analytics only and decides nothing. No
  hidden coupling, no "session says en but request says hi" conflicts.

## 4. Frontend specifics

- **Library:** next-intl (App Router native, free, tiny).
- **Routing:** all pages live under `app/[locale]/…`; middleware
  validates the locale segment against `['en', 'hi']`.
- **Fonts — this was a real gap:** Manrope contains **no Devanagari
  glyphs**. Stack: `Manrope` + `Noto Sans Devanagari` (both free on
  Google Fonts), loaded via `next/font` with subsets per locale.
  Devanagari needs slightly more vertical room: `html[lang="hi"]`
  gets a ~1.15× line-height adjustment on instruction-size text.
- **`<html lang>`** set to the active locale (screen readers pick the
  right voice); `dir` stays `ltr` for both.
- **Voice input:** Web Speech API with `recognition.lang = 'hi-IN'`
  or `'en-IN'` from the active locale. Free-text is sent as typed —
  Hinglish (Hindi in Latin script) is expected real input and is
  handled by the model, not pre-translated.
- **Numbers and emergency services:** 112/108 are identical in both
  languages; digits stay Latin (standard practice for Hindi UI and
  matches the mockups).
- **All user-visible error text** comes from message files keyed by
  the API's machine error code (`errors.RATE_LIMITED`, …). The
  backend never writes a sentence a user sees.

## 5. AI output language

Decision: **the model generates guidance directly in the requested
language.** No translate-after step — translation adds latency, a
second failure point, and costs quota.

- The **system prompt stays English** (instruction-following is
  strongest in English) and contains an explicit output-language
  clause filled per request:
  *"Write every human-readable string value in {Hindi (Devanagari
  script) | English}. Keep all JSON keys and enum values in English
  exactly as specified."*
- Structure stays English: `risk_level: "URGENT"` even when `summary`
  is Hindi. The frontend renders enums through its own message files.
- **Output-language verification:** cheap script check on the
  generated display strings (Devanagari codepoint ratio for `hi`,
  Latin for `en`). Wrong language → treated exactly like a schema
  failure → one retry → fallback KB. A Hindi user never receives
  English guidance labeled as an answer.
- The safety filter runs the list matching the *output* language
  (`safety/hi.yaml` for Hindi output).

## 6. Content authoring workflow (you are the CMS)

1. Author/edit the English YAML in `content/en/`.
2. Mirror it in `content/hi/` — same file name, same IDs, translated
   display strings only. Hindi register: simple, spoken Hindi
   (bolchaal ki bhasha), not formal shuddh Hindi — the audience is a
   stressed person, possibly low literacy.
3. `pytest tests/unit/test_content_parity.py` locally (CI runs it
   anyway) — fails listing exactly which IDs/keys are missing where.
4. Commit. Deploy reloads content. Git history is the audit trail.

Example — the same question in both trees:

```yaml
# content/en/questions/burn.yaml
- id: burn_size
  text: "How large is the burn?"
  options:
    - id: smaller_than_palm
      text: "Smaller than the palm"
    - id: larger_than_palm
      text: "Larger than the palm"
      escalates_to: URGENT

# content/hi/questions/burn.yaml
- id: burn_size
  text: "जलन कितनी बड़ी है?"
  options:
    - id: smaller_than_palm
      text: "हथेली से छोटी"
    - id: larger_than_palm
      text: "हथेली से बड़ी"
      escalates_to: URGENT
```

Same IDs, same `escalates_to` (safety metadata is machine-facing and
must be identical — the parity check enforces that too). Only `text`
differs.

## 7. What is *not* done, on purpose

- No third language scaffolding — `en`/`hi` are literals where it
  keeps the code simpler; adding a language is a grep, not a
  framework.
- No auto-detection of browser language beyond the cookie default —
  in an emergency, a wrong guess is worse than a visible toggle.
- No transliteration or machine translation of stored content — every
  Hindi string is human-written or AI-generated-then-filtered, never
  mechanically converted.
